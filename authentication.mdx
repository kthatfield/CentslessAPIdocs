Every endpoint except `GET /api/v1/health`, `GET /api/v1/version`, the public jurisdiction lookups, and the countdown requires an API key sent in the `x-api-key` header.

```bash
curl https://api.centsless.org/api/v1/stats \
  -H "x-api-key: $CENTSLESS_API_KEY"
```

## How keys are issued

Keys are issued in two ways.

| Path | Who | What they get |
|---|---|---|
| Partner provisioning | A POS platform or integrator | A **partner key** (`centsless_partner_…`). Registering a merchant through the partner API issues that merchant its own **merchant key** (`centsless_merch_…`). |
| Admin key management | Centsless | Keys of any role through `POST /api/v1/admin/keys`, with an optional expiry. |

There is no self-service signup and no shared test credentials. To start a pilot, [request one](https://www.centsless.org/contact) and a partner key is provisioned for you.

## Roles and permissions

Each key carries one role. The role decides which permissions the key holds, and each endpoint names the permission it requires.

| Role | Permissions | Typical holder |
|---|---|---|
| `admin` | `*` | Centsless operations |
| `partner` | `transaction:create`, `transaction:read`, `stats:read`, `audit:read`, `export:standard`, plus merchant onboarding under `/api/v1/partner/*` | POS platform |
| `merchant` | `transaction:create`, `transaction:read`, `transaction:override`, `transaction:void`, `transaction:refund`, `tip:create`, `tip:pool`, `tip:payout`, `tip:analytics`, `export:standard`, `stats:read` | A merchant registered by a partner |
| `auditor` | `transaction:read`, `audit:read`, `export:full`, `logs:read` | Compliance review, external audit |
| `readonly` | `transaction:read`, `stats:read` | Dashboards |

A merchant key is scoped to its merchant. Transactions sent with it are linked to that merchant's record, registered locations resolve only for that merchant, and the early-adoption settings endpoint accepts only that merchant's id.

A partner key is scoped to its partner. It can register and manage the partner's own merchants and read analytics across them. An admin key may act on any partner's behalf by passing `partner_id` as a query parameter or `x-partner-id` as a header.

## Internal service key

Three provisioning endpoints under `/api/v1/provision/*` are called by Centsless's own portal backend, not by partners. They require the `INTERNAL_SERVICE_KEY` shared secret in the `x-service-key` header and are documented for completeness.

## Key hygiene

- Keys are stored hashed. A key is shown once, at creation, and cannot be retrieved afterward. Rotate a partner key with `POST /api/v1/admin/partners/{partnerId}/rotate-key`; the old key stops working immediately.
- Revoke any key with `DELETE /api/v1/admin/keys/{keyId}`.
- Keys may carry an expiry (`expires_in_days` at creation). An expired key is rejected with `401`.
- Every rejected request (missing, invalid, or expired key; insufficient permission) is logged as a security incident with the endpoint and the source IP.

## Errors

| Status | `error` | Meaning |
|---|---|---|
| `401` | `UNAUTHORIZED` | No key, an unknown key, or an expired key |
| `403` | `FORBIDDEN` | The key's role lacks the required permission, or the resource belongs to another merchant or partner |
| `429` | `RATE_LIMIT_EXCEEDED` | See [Rate limits](/reference/rate-limits) |

<Warning>
Treat keys as production credentials from the first day. There is no separate sandbox environment; a pilot runs against the production engine with its own partner and merchant records.
</Warning>
